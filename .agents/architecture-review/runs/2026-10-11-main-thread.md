# Independent architecture review: interactive owner-thread paths and collaborators

Scope: historical reviewed commit `a78d4b5d`, interactive session event loop, playback/subtitle/geometry/rendering, hover/dictionaries, mining/preview/sidebar/profiles, and shutdown. This is a scoped review, not a whole-repository architecture verdict. No implementation changes.

Archived review of that commit, not a finding about current main. Source paths, line numbers and
“current” statements below refer to the reviewed revision. Later fixes are outside this report.
The referenced `/tmp` outputs and ignored `vibe/` harness are not retained in this archive; their
absence limits reproduction of the recorded measurements.

The product is a local immersion workstation inside mpv: watch with FSRS coloring, hover dictionary entries, mine grounded cards without leaving the video, and preserve Syncplay playback ownership. These goals come from README.md:7–14, 38–58, 72–82 and the actual command table generated by `poe arch-map`. Responsiveness, correct cue/card identity, bounded optional work, and one visible surface matter more than generalized extensibility.

The core principles fit the product. The single owner-thread publication boundary, observed playback projection, background expensive work, and generation-qualified publication are useful. The remaining weakness is incomplete execution of that boundary: presentation and admission helpers can still perform synchronous dependency work before the worker lane is reached. I found four concrete stall mechanisms and one smaller simplification opportunity. I did not establish a current live deadlock or quantify normal-case latency.

## Evidence and actual thread map

- `SessionController.run/pump` (`app/session/controller.py:40–63`) hands the owner thread to SessionLoop. The loop drains events and invokes the reactor/command performer synchronously (`runtime/loop.py:119–159, 170–185`). Reducer purity does not imply that effect application is nonblocking.
- The IPC reader and writer are separate threads. A synchronous `MpvIPC.command` nonetheless waits for its future on the **calling** thread, with a default ten-second timeout (`mpvio/ipc.py:434–455`). Background replies avoid a circular dependency on mailbox drainage; that is why a synchronous query is a bounded stall here, not automatically a deadlock.
- Annotation, geometry rendering, engaged tooltip work, speculative rendering and preview preparation have workers. Normal JobBroker terminal callbacks return through the owner-thread mailbox; this is not a universal callback-thread guarantee. Interaction-presenter acknowledgements can execute on the presenter thread. Preview preparation now uses a capacity-one lane without inline fallback (`features/preview/preview_controller.py:44–47, 188–239`).
- Startup seeding is synchronous by design; it is distinct from steady-state turn handling. The subtitle artifact work below also runs on live track changes and file-loaded episode transitions, so it cannot be dismissed as startup-only.
- Generated evidence supplied for this run: `/tmp/saitenka-main-thread-arch-map.txt` reports 307 modules, 1,392 import edges, five annotation-only cycles and zero real cycles; `/tmp/saitenka-main-thread-reducer-purity.txt` reports 20 registered reducers, no ambient readings reaching branches, and two emitted-effect stamps. These meters do not measure callback latency, foreign code, or all decision functions. Port-probe census has 44 unresolved receivers; it does not prove the unresolved sites safe.

## Findings

### P1 — Mining admission and clicks bypass the playback snapshot and wait on mpv

Axes: efficiency, resilience, soundness of the snapshot boundary.

`PlaybackObservationController.number/text/mapping/sequence` always call `query`, unlike `value`, which uses the observed projection (`session/playback_observation.py:140–164`). All of `path`, `sub-start`, `sub-end`, `time-pos`, `mouse-pos`, and `track-list` are already observed (same file:23–100).

The configured word-mining path performs these operations on the owner thread:

1. `MineCommandCoordinator.inputs` calls `bookmark.has_active_cue` unconditionally, even for word mining (`features/mining/mine_adapter.py:94–103`); the bookmark endpoint queries path/start/end (`:41–48`, wired at `session/builder.py:1082–1090`).
2. `mining.mine_target` calls `_encounter()` to select a token (`features/mining/mining_controller.py:447–450`). `MiningEncounterSource.capture` queries start/end/path/time-pos (`mining_encounter.py:31–51`).
3. `mine_index` calls `_operation`, which captures the encounter again (`mining_controller.py:452–454, 675–681`).

A successful configured word mine therefore has **11 sequential property queries before worker dispatch**, with ordinary non-null playback facts. Click routing separately queries `mouse-pos` via `mapping` (`session/interaction_adapter.py:134–144`). If mpv accepts writes but delays replies during a seek or overload, the session cannot settle later cue, hover, timer, or close events until each synchronous wait ends. A query timeout is bounded; the eleven-call sum is not a claim that a real command currently takes 110 seconds, since failed admission short-circuits and failed target selection can stop the path.

Discriminator: the snapshot is installed and observes these properties, but `text/number/mapping` do not consult it. A stdlib diagnostic executed the AST-extracted production `has_active_cue`, `number`, `text`, and `capture` bodies against a recording query stand-in: three admission reads plus two four-read captures produced eleven queries. This measured call count, not real player latency. The synchronous production call sites above establish reachability independently of that stand-in.

Reproducible harness: `vibe/plans/main_thread_query_counter.py`. From the repository root run `UV_CACHE_DIR=/tmp/saitenka-architecture-uv-cache uv run --no-project --python 3.14 vibe/plans/main_thread_query_counter.py`. The harness manually invokes one admission and two capture bodies; it verifies the per-body count, while the source call chain establishes their production composition. It is not a full command-ingress integration test.

Age: encounter capture existed by `411e92d1` (2026-09-05, move card work off interaction loop); click routing exists by `cb62bc65` (2026-08-29). Both predate the latest main-thread-waits fix `586b5cff` (2026-10-10).

Smallest remedy: use observed playback facts for admission and encounter capture, with explicit synchronous queries reserved for genuinely necessary live probes. Avoid building a full encounter solely to choose a token; sample token/cue facts directly or capture once. Cover the real command ingress with a stand-in that refuses synchronous reads after seed installation. Preserve cue retirement ordering and mining target qualification.

### P1 — Paused repaint reissues every live overlay with synchronous IPC

Axes: efficiency and coherence of the presentation boundary.

`SessionController.pump` calls `schedule_paused_nudge` after settlement (`session/controller.py:49–52`). If overlay operations changed and playback is paused, `SessionPresentation.schedule_paused_nudge` arms a zero-delay timer, with immediate fallback when scheduling fails; its callback calls `LifecycleSurfaces.repaint` (`session/support.py:105–122`; `lifecycle_surfaces.py:157–163`). That delegates to `Overlay.repaint`, then `_reissue_live`, which calls `ipc.command("overlay-add", ...)` **sequentially for every live overlay** (`mpvio/osd.py:414–428, 561–568`). The timer callback runs through the owner-thread terminal path; it is not a worker transition.

This is a core paused study path: a sidebar, help, preview or other lifecycle surface changes `overlay.ops`, and its subsequent repaint waits on the owner thread even though ordinary lifecycle publication uses correlated async commands. The neighboring overlay visibility action uses the same synchronous reissue loop when restoring surfaces and synchronous removes when hiding (`osd.py:546–558`; `lifecycle_surfaces.py:148–155`). Pure TIP-only presenter updates need not increment `ops`; the proven trigger is a paused change that does increment it, and repaint then reissues whichever overlays are in `_live`.

Failure scenario: a delayed reply in paused mpv stalls later cue/input/timer processing per live surface. The default wait is ten seconds per command, but no real latency or regularity is asserted. The repaint deliberately does not increment `ops`, so this is **not** an infinite feedback loop.

Discriminator: capture the owner-thread stack through `_flush_paused_nudge -> repaint -> _reissue_live -> Future.result`. Ordinary deferred interaction rendering is on another path and does not falsify this path. Conversely, TIP-only drawing without an `ops` increment does not prove this timer fires.

Age: paused repaint itself was introduced in `a4cf04b6` (2026-07-26); the current reissue helper is present by `615be157` (2026-08-25).

Smallest remedy: retain the paused-composition poke, but enqueue correlated repaint/visibility commands through the existing egress/presenter boundary and hold each BGRA path until its terminal. Do not remove the poke or free held paths after enqueue: both behaviors have concrete platform/lifetime reasons in the existing code. Verify paused lifecycle presentation with an IPC stand-in whose synchronous command path fails.

### P1 — Track replacement can run unbounded ffmpeg extraction on the owner thread

Axes: resilience, efficiency, fitness for purpose.

`CueCoordinator.rebuild_sub_index` directly invokes `build_sub_index_for_current_track` (`session/cue_coordinator.py:472–481`). That function queries the selected track, resolves fonts, and calls `extract_embedded_track` on a cache miss (`embedded_subs.py:121–162`). The extraction uses `subprocess.run(..., check=True, capture_output=True)` with **no timeout or cancellation** (`embedded_subs.py:66–86`).

Live reachability is explicit: observed subtitle selection applies `_adopt_selected_subtitle` (`session/builder.py:862–864`), which invokes `on_primary_changed` and may rebuild the index (`builder.py:170–190`; `subtitle_modes.py:339–351`). Profile switching also calls rebuild synchronously (`features/profiles/profile_integration.py:95–115`). `SessionController._drain_event(FileLoaded)` calls EpisodeWatch synchronously (`controller.py:80–86`); the installed run/attach reslot hooks call rebuild again (`launch/run.py:725–734, 817`; `commands/attach.py:118, 200–207`).

Failure scenario: first selection of an uncached embedded track in a large, slow, damaged or temporarily unavailable container leaves ffmpeg scanning or waiting while the session ceases to drain its mailbox. Playback may continue in mpv, but overlay interactions and graceful stop cannot proceed. Font preparation is another part of the same synchronous transaction: `resolve_track_fonts` performs property queries and invokes `subtitle_fonts.resolve` (`embedded_subs.py:96–118`), which reads/probes/extracts font sources (`subtitle_fonts.py:354–397, 462–519`). Its subprocesses have bounds; they still hold the owner turn. No normal-case duration is asserted.

Discriminator: the selected track is uncached and embedded; follow the **observed sid change**, not just launch setup. The call chain enters `subprocess.run` on the session executor; there is no submitter or worker transition in between. An external track or warm cache avoids subtitle extraction but does not eliminate all font work.

Age: embedded extraction predates the modularization commit; `git log --follow -S 'def extract_embedded_track'` traces it to `f6106135` (2026-07-27). Font resolution arrived in `0c40b916` (2026-08-23).

Smallest remedy: treat artifact/index/font preparation as one generation-qualified background operation with a subprocess timeout/cancellation. Keep mpv's current subtitle pixels and retire stale interaction geometry while preparation is pending; install only if source, track, profile and connection still match. Reuse existing lane/publication patterns rather than adding another event architecture. A timeout alone prevents an infinite wait but leaves the UI frozen for the entire bound.

### P1 — Stopping preview audio can synchronously hold cue retirement for five seconds

Axes: resilience and efficiency.

The preview's media **preparation** moved to a worker, but process retirement remains synchronous. `miner_ui._stop_preview_audio` clears the panel handle and calls `kill_process_tree(proc)` (`features/preview/miner_ui.py:197–203`). `show_preview`, `hide_preview`, and replacement audio playback all use it (`:207, 241–244, 282`). `kill_process_tree` defaults to five seconds and calls `psutil.wait_procs(tree, timeout=timeout)` before hard killing survivors (`app/procutil.py:18–46`; the stdlib fallback also waits).

This reaches normal cue turnover: `CueCoordinator._set_subtitle_inner` calls `preview.retire_cue` (`session/cue_coordinator.py:226–232`), and the endpoint calls `hide` (`features/preview/preview_endpoint.py:104–119`). A launched audio player or descendant that ignores or delays termination therefore delays cue retirement and the whole owner loop for up to the cleanup bound. This is conditional on a live slow-to-exit player; it is not five seconds for every preview or every cue.

Discriminator: preparation completion runs successfully, then an **audio subprocess** survives termination. Observe `psutil.wait_procs` in the owner-thread stack; a slow `ffprobe` in preparation would be a different, already-offloaded cause.

Age: the stop-on-dismiss call is traced through moves to `effd9582` (2026-08-09, fix #251). It survived the recent preparation offload.

Smallest remedy: detach the handle immediately, issue termination immediately, and reap/escalate on bounded background cleanup. Keep stopping the old clip on every dismiss/replacement; simply deleting cleanup would restore orphaned playback. Add a controlled stubborn-child test through the preview-dismiss/cue path if changing it, without using real mpv.

### P2 — Tooltip speculation repeats annotation work before it reaches a worker

Axes: simplicity and efficiency; normal-case performance impact unmeasured.

`InteractionCoordinator.settle` invokes `tooltip.update_prefetch` (`session/interaction_adapter.py:149–156`). This calls `TooltipPreparationController.update`, then `prefetch.update_prefetch`, which synchronously builds the job list before `schedule` (`features/tooltip/tooltip_controller.py:641–648`; `preparation.py:336–352`; `prefetch.py:380–419`). `_head_prefetch_items` passes raw `ports.tokenizer.tokenize` and `head.scorer.score_line` into `_head_candidates_for_text` (`prefetch.py:495–563`). The ordinary default considers one upcoming cue (`config.py:334–336`). Plain decode lookahead is off by default (`:320–323`), so `_lookahead_items` is an additional opt-in path, not the default culprit.

The annotation subsystem independently tokenizes/scores episode cues on a worker and caches them (`features/annotation/annotation_controller.py:371–389, 549–580, 599–629`); it has a generation-qualified `event_annotation` API (`:289–301`). Thus speculative tooltip admission has a second tokenization/scoring path and ignores already-warmed annotation results. An engagement change can revisit the same future cue because the scheduling key is `(text, engaged)` (`prefetch.py:398–402`). The token-probe cap limits candidate enumeration after `tokenize` and `score_line`, not the cost of those calls.

Discriminator: spy on tokenizer/scorer thread identities while driving the production settlement path with an indexed upcoming cue and a scorer. Calls made before `schedule` are owner-thread work; heavy panel rendering after submission is not. A warmed annotation cache currently cannot remove these raw calls.

Age: the head-prefetch machinery exists by `efeed30a` (2026-08-18, speculative prefetch broker); shared event annotation arrived later in `db1c4936` (2026-09-26).

Smallest remedy: feed speculative admission already-prepared immutable annotation results, or perform cold candidate preparation on a worker and publish a qualified result. Do **not** blindly replace raw tokenization with a cache call on the owner thread: cold `event_annotation` computes synchronously, and annotation uses dictionary-aware/event-grouped tokenization whereas this path currently does not. Preserve selective rendering and its queue/RSS bound. Profile before claiming a frame-budget violation or deleting a useful feature.

## What to keep

- The ordered owner-thread boundary. It gives cue retirement priority over later cue-dependent commands and provides one place to reject late results. Independent IPC reply resolution is useful and prevents query waits from requiring the event consumer itself to run.
- Feature owners rather than a controller-shaped bag of capabilities. The host is now small (`session/controller.py`), while mining, profile, tooltip, and cue/episode conjunctions name their authority. A 14-field preview endpoint is review evidence, not proof of a second god object.
- Background preview preparation with cancellation, latest-request identity, destination correlation, failure dismissal, and no inline rejection fallback (`preview_controller.py:126–239`). The missing audio retirement boundary should be repaired without undoing this.
- Native subtitle pixel ownership independent of interactive geometry. Degradation can remove hit boxes while mpv keeps the subtitle visible, which directly serves watching and Syncplay.
- The explicit close ledger and ordered close plan, including the shared worker-lane deadline (`session/close_plan.py:194–221, 225–246`). Exceptions are recorded and later steps still run (`close_ledger.py:49–75`). This isolates exceptions, not arbitrary non-returning functions; the source does not claim otherwise.
- Warm-only tooltip composition and bounded latest-request workers. Their coherence is more valuable than making all work enter a uniform reducer/effect spelling.

## What to cut, with the loss

Cut the distinction between “observed playback” and “typed playback helper” when the latter silently means synchronous IPC: keep explicit `query/probe` for callers that actually require them. Loss: those helper callers see the ordered event projection rather than a fresh live reply; this is the desired semantic input for cue-bound admission, but migration should inspect explicit sampling use cases individually.

Cut duplicate full encounter construction for target selection; keep one immutable admitted encounter for worker work. Loss: repeated live sampling disappears, which also improves consistency between the selected token and media timestamps.

Consolidate annotation preparation used by tooltip speculation where semantics agree. Loss: a cold future-cue head may become eligible a turn later; verify that against hover responsiveness before changing defaults. Do not delete the speculative rendering tier merely because a second tokenizer path is wasteful.

## Principles answer

The strongest case against the current model is that a single-user, single-session local tool has accumulated command specs, snapshot reducers, owner stores, effects, correlators, lanes, capability dataclasses and close ledgers. A simpler callback application could express many ordinary toggles with fewer concepts, and the current ceremonies do not by themselves keep I/O off the owner thread.

Replacing the runtime wholesale would be the expensive answer to the wrong problem. It would require re-establishing ordering, connection epochs, stale-result rejection, teardown and fake-runtime behavior already encoded here, while the four concrete waits above would remain waits until their call sites changed. Uniformly making every synchronous bounded action an effect would add hops without eliminating the expensive calls. Keep ordering and qualified publication; use direct bounded-owner actions where policy is already owned; repair the actual execution boundaries with existing lanes. These scoped findings do not establish a whole-system redesign.
